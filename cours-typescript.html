Préambule

Ce que TypeScript fait, et ce qu'il ne fait pas

0.1Un correcteur, pas un langage d'exécution

TypeScript est du JavaScript auquel on a ajouté des annotations de type. Ces annotations servent uniquement pendant que vous écrivez et pendant la compilation. Elles sont ensuite entièrement supprimées. Le navigateur et Node.js n'exécutent que du JavaScript ordinaire : ils n'ont jamais entendu parler de TypeScript.

Ce point est fondamental, et il explique un comportement qui déroute souvent. Prenons du vrai code du projet :

: Date et : number ont disparu. Il n'en reste rien.

La conséquence la plus importante

TypeScript ne peut rien vérifier à l'exécution. Si une donnée arrive de l'extérieur — un formulaire, une requête HTTP, une réponse d'API — le fait de lui avoir donné un type ne garantit absolument rien. C'est précisément pour cela que app/actions/reservations.ts revalide chaque champ à la main : le type dit « ce devrait être une chaîne », le code doit vérifier « c'en est bien une ».

Alors à quoi ça sert ?

À trois choses, toutes utiles avant l'exécution :

  • Attraper des erreurs pendant que vous tapez. Une faute de frappe dans un nom de propriété est signalée immédiatement, pas à minuit en production.
  • Documenter. La signature validateReservation(input: ReservationInput, today: string) dit tout ce qu'il faut savoir pour l'appeler.
  • Rendre l'éditeur intelligent. L'autocomplétion, le « aller à la définition », le renommage sûr — tout cela vient des types.

Les deux commandes à connaître

--noEmit signifie « contrôle seulement ». C'est la commande à lancer quand vous voulez savoir si votre code « tient » sans attendre une compilation complète.

Partie 1

Les fondations

Tout ce qu'il faut pour lire les fichiers de données du projet : apartments-data.ts, site-sections.ts, contact-data.ts.

1.1Types de base, et l'inférence

Les types primitifs sont string, number, boolean, plus null et undefined. Notez les minuscules : String avec une majuscule existe aussi mais désigne autre chose, et n'est pratiquement jamais ce que vous voulez.

Le plus important : vous n'avez presque jamais besoin de les écrire. TypeScript déduit le type à partir de la valeur. C'est ce qu'on appelle l'inférence.

Aucune annotation, et pourtant SECTION_SCROLL_DURATION est de type number. Écrire const SECTION_SCROLL_DURATION: number = 1.5 serait du bruit : l'information est déjà dans la valeur.

La règle pratique du projet, et une bonne règle en général : annotez ce qui entre dans une fonction, laissez TypeScript déduire ce qui en sort.

Le type any, et pourquoi il n'apparaît pas ici

any veut dire « désactive les vérifications pour cette valeur ». Il se propage : tout ce qui touche un any devient incontrôlé. Cherchez any dans ce projet — vous n'en trouverez aucun. Quand un type est réellement inconnu, la bonne réponse est unknown, qui oblige à vérifier avant d'utiliser.

1.2Annoter une fonction

La forme est nom(paramètre: Type): TypeDeRetour. Le type de retour est presque toujours omis, car déduit.

Décortiquons :

  • target: string — paramètre obligatoire, annoté.
  • duration = SECTION_SCROLL_DURATION — valeur par défaut. Pas d'annotation nécessaire : la valeur par défaut étant un number, le paramètre est un number. Et parce qu'il a une valeur par défaut, il devient facultatif à l'appel : scrollToSection("#contact") fonctionne.
  • Le type de retour est boolean, déduit des return false / return true.

Les trois façons d'écrire une fonction

La flèche => se lit « donne ». (part) => String(part) : « prends part, donne String(part) ». Quand le corps tient sur une expression, le return est implicite. Avec des accolades, il redevient obligatoire :

Dans le cas b, TypeScript déduit le type de retour void — « rien ». C'est une source d'erreur classique quand on ajoute des accolades pour insérer un console.log et qu'on oublie le return.

1.3Décrire un objet avec type

Pour donner un nom à la forme d'un objet, on écrit un alias de type.

Ce type dit : « un Apartment est un objet qui a obligatoirement slug, price, rooms, area et src, et éventuellement perDay et seats ». Chaque propriété est séparée par un point-virgule (une virgule marche aussi).

Une fois nommé, on s'en sert comme de n'importe quel type :

Apartment[] se lit « tableau de Apartment ». Les crochets après un type signifient toujours « tableau de ». Ici l'annotation est utile, contrairement au cas de SECTION_SCROLL_DURATION : sans elle, TypeScript déduirait un type approximatif à partir du premier élément, et ne signalerait pas une faute de frappe dans la trentième ligne du tableau.

Et interface ?

Vous rencontrerez souvent interface Apartment { … } dans d'autres projets. Pour décrire un objet, les deux sont pratiquement équivalents. type est plus général : il sait aussi nommer une union (type Slot = "morning" | "afternoon"), ce dont interface est incapable. Ce projet n'utilise que type, par cohérence. Gardez la même habitude.

Attention à ne pas confondre

Le ? a trois emplois totalement différents en TypeScript. Après un nom de propriété (perDay?: boolean) il veut dire « facultatif ». Entre deux expressions (a ? b : c) c'est le ternaire. Avant un point (forwarded?.split) c'est le chaînage optionnel, vu en 1.8. Le glossaire final récapitule tout.

1.5Unions et types littéraux

La barre verticale | signifie « ou ». Elle permet de dire qu'une valeur est de l'un ou l'autre type.

Regardez bien : les membres ne sont pas des types, ce sont des chaînes précises. C'est ce qu'on appelle un type littéral. SectionKey n'est pas « une chaîne », c'est « exactement l'une de ces cinq chaînes ».

C'est une des idées les plus utiles de TypeScript, et elle est partout dans ce projet :

Le bénéfice est double : l'éditeur propose les valeurs valides en autocomplétion, et as="span" devient une erreur de compilation plutôt qu'un bug silencieux.

Une union peut aussi mélanger un type et une valeur :

string | null : soit une adresse, soit rien. Et parce que null fait partie du type, TypeScript refusera target.slice(1) tant que vous n'aurez pas écarté le cas null. Ce qui est exactement ce que fait la ligne suivante du fichier :

target ? … : [] écarte null. Dans la branche vraie, TypeScript sait que target est forcément une string et autorise .slice(1). On appelle cela le rétrécissement (section 2.6).

1.7null, undefined et le mode strict

Le fichier tsconfig.json du projet contient "strict": true. C'est ce réglage qui rend TypeScript réellement utile, et c'est lui qui provoque la majorité des erreurs que vous rencontrerez au début.

En mode strict, null et undefined ne font pas partie des autres types. Une string ne peut pas être null. Si une valeur peut être absente, il faut le dire explicitement, et le vérifier avant usage.

getLenis() renvoie donc Lenis | null. Tout appelant est forcé de gérer le cas null :

Sans le if, TypeScript refuserait de compiler : « Object is possibly null ». Cette contrainte n'est pas une punition, c'est la fonctionnalité : elle élimine par construction la famille d'erreurs la plus courante en JavaScript, Cannot read properties of null.

1.8?. et ??

Deux opérateurs conçus exactement pour gérer l'absence sans écrire des cascades de if. Le serveur les utilise tous les deux dans la même fonction.

?. — le chaînage optionnel. list.get() renvoie string | null : l'en-tête peut ne pas exister. forwarded?.split(",") se lit « si forwarded n'est ni null ni undefined, appelle .split() ; sinon, donne undefined et n'appelle rien ». Cela remplace :

Le second ?., dans [0]?.trim(), protège contre un tableau vide : morceaux[0] serait alors undefined.

?? — le coalescement nul. a ?? b donne a, sauf si a vaut null ou undefined, auquel cas il donne b.

seen.get(key) renvoie number[] | undefined — une Map ne contient pas forcément la clé demandée. ?? [] fournit un tableau vide dans ce cas, ce qui permet d'enchaîner .filter() sans test préalable.

Le piège classique : ?? contre ||

|| se déclenche sur toute valeur « faussée » : 0, "", false, NaN, en plus de null et undefined. ?? ne se déclenche que sur null et undefined.

0 || 10 donne 10 — souvent pas ce qu'on veut.
0 ?? 10 donne 0 — presque toujours ce qu'on veut.

Dans callerKey(), le || est délibéré : une chaîne vide doit basculer sur la valeur suivante, exactement comme null. Dans ?? [], le ?? est délibéré aussi : un tableau vide existant est une valeur valable qu'il ne faut pas remplacer.

Voici le motif le plus élégant du projet, et il mérite qu'on s'y arrête. Regardez la fin de dictionary.ts :

typeof en — en position de type, pas de valeur — signifie « le type que TypeScript a déduit pour l'objet en ». Personne n'a écrit à la main le type du dictionnaire : il est extrait de la valeur anglaise, qui devient la référence.

Ce que ce motif vous achète

Si vous ajoutez une clé en anglais et l'oubliez en français, le projet ne compile plus. Si vous faites une faute de frappe dans le français, il ne compile plus non plus. La traduction ne peut pas dériver en silence.

C'est exactement ce qui s'est passé quand nous avons ajouté le bloc reserve : il a fallu l'écrire dans les deux langues, le compilateur ne laissait pas le choix.

Ne confondez pas les deux typeof

En JavaScript, typeof x === "string" est un test exécuté à l'exécution qui renvoie une chaîne. Le projet l'utilise dans read() et dans le piège à robots.

En TypeScript, typeof en écrit à l'endroit où l'on attend un type est une opération de compilation qui ne produit aucun code. Même mot, deux mondes.

2.4L'accès indexé : piocher dans un type

On peut lire l'intérieur d'un type avec des crochets, comme on lirait une propriété d'objet.

Décomposons cette ligne, qui est dense :

  1. Dict est le type du dictionnaire (section 2.3).
  2. Dict["listings"] est le type de sa propriété listings, c'est-à-dire l'objet { "the-penthouse": {…}, "garden-villa": {…}, … }.
  3. keyof prend un type d'objet et donne l'union de ses clés : "the-penthouse" | "garden-villa" | "skyline-apartment" | …

Donc slug ne peut être que le nom d'une annonce qui existe réellement dans le dictionnaire. Écrire slug: "the-penthous" (faute de frappe) est une erreur de compilation. Et si vous supprimez une annonce du dictionnaire, toutes les données qui la référencent cessent de compiler.

L'autre forme d'accès indexé concerne les tableaux :

(typeof SLOTS) vaut readonly ["morning", "afternoon"]. L'indexer par [number] signifie « le type de ce qu'on obtient en indexant par n'importe quel nombre », c'est-à-dire l'union de tous les éléments : "morning" | "afternoon".

Résultat : la liste des créneaux est écrite une seule fois. Elle sert à la fois de valeur exécutable (pour SLOTS.includes(...)) et de type. Ajouter "evening" au tableau met à jour le type automatiquement.

2.5Les unions discriminées

Si vous ne deviez retenir qu'une seule idée de ce cours, ce serait celle-ci. C'est le motif structurant du projet, côté client comme côté serveur.

Une union discriminée, c'est une union d'objets qui partagent tous une propriété commune servant d'étiquette. En lisant l'étiquette, TypeScript sait de quelle variante il s'agit et débloque les propriétés correspondantes.

L'étiquette est ici type. Ce qui rend le motif puissant, c'est que les variantes n'ont pas les mêmes propriétés. La liste n'a pas de slug — et c'est correct, puisqu'elle les affiche toutes.

Dans la première branche, écrire view.slug serait une erreur de compilation : la variante "list" n'en a pas. Dans la deuxième, view.slug est autorisé et de type string, pas string | undefined. TypeScript a suivi le raisonnement tout seul.

Le même motif, côté serveur

Ce type décrit tout ce que la Server Action peut répondre. Seule la variante "invalid" transporte des erreurs — les autres n'en ont pas besoin. Le formulaire lit l'étiquette et sait quoi afficher :

2.6Rétrécissement et gardes de type

Le rétrécissement (narrowing) est le mécanisme par lequel TypeScript réduit un type au fil des tests que vous écrivez. Vous l'utilisez sans le savoir depuis la section 1.7.

Ce style — « sortir tôt si la valeur manque » — s'appelle une clause de garde. Il évite d'imbriquer tout le corps de la fonction dans un if, et il rétrécit le type pour tout ce qui suit.

2.7Le point d'exclamation

Un ! après une expression est l'assertion de non-nullité. Il dit : « je sais que ce n'est ni null ni undefined, tais-toi et fais-moi confiance ».

.find() renvoie Apartment | undefined, car rien ne garantit en général qu'un élément corresponde. Mais ici, la ligne précédente a fait échouer la requête si le slug n'était pas dans APARTMENTS. Le ! reflète ce raisonnement.

Le ! est une dette

Chaque ! est une vérification que vous retirez au compilateur pour la prendre en charge vous-même. Si quelqu'un déplace un jour la validation ou change son ordre, le ! devient un mensonge et l'application plante à l'exécution — sans aucun avertissement.

C'est pour cela qu'il n'y en a qu'un seul dans tout le projet, et qu'il est accompagné d'un commentaire qui explique pourquoi il est légitime. Si vous êtes tenté d'en écrire un, demandez-vous d'abord si une clause de garde ne ferait pas mieux l'affaire.

Attention à ne pas le confondre avec le ! de négation, qui se place avant : if (!root) return; veut dire « si root est faussé ». Deux opérateurs, même caractère, positions opposées.

3.1Deux machines, deux mondes

Une application Next.js s'exécute à deux endroits différents, et c'est la source de la majorité des confusions quand on débute.

Serveur (Node.js)Navigateur
Où Votre machine en dev, l'hébergeur en production Le téléphone ou l'ordinateur du visiteur
Voit Le système de fichiers, les variables d'environnement, la base de données, les clés d'API Le DOM, la souris, le clavier, localStorage
Ne voit pas window, document, localStorage Tout secret. Absolument tout ce qui y arrive est public.
Dans ce projet app/actions/reservations.ts, app/page.tsx, app/layout.tsx Tout fichier commençant par "use client"

Un composant sans directive est un Server Component : il s'exécute uniquement sur le serveur, et seul son résultat HTML parvient au navigateur. C'est le défaut dans Next.js moderne.

Dès qu'un fichier a besoin d'interactivité — un état, un gestionnaire de clic, un effet — il doit devenir un Client Component avec "use client".

Ce test est là parce que ce module est évalué aussi sur le serveur, lors du rendu initial. Sur le serveur, window n'existe pas : y accéder directement provoquerait ReferenceError: window is not defined. C'est l'erreur de débutant la plus fréquente en Next.js.

3.2"use client" et "use server"

Ces deux chaînes en tête de fichier ne sont pas des commentaires : ce sont des directives lues par le compilateur. Elles marquent une frontière.

"use client"

« Ce fichier, et tout ce qu'il importe, part dans le navigateur. » Il est requis dès qu'on utilise un hook (useState, useEffect…) ou un gestionnaire d'événement.

"use server"

Le contraire, et il est plus subtil : « ce fichier reste sur le serveur, mais ses exports deviennent appelables depuis le navigateur ».

Concrètement, à la compilation, Next.js remplace le corps de requestViewing dans le bundle client par une simple référence chiffrée. Quand le formulaire l'« appelle », le navigateur envoie en réalité une requête POST, et c'est le serveur qui exécute la vraie fonction.

La règle qui nous a coûté un bug

Un fichier "use server" ne peut exporter que des fonctions async. Rien d'autre. Nous avions d'abord exporté INITIAL_STATE, un simple objet, depuis ce fichier — et l'application plantait au rendu de la page :

A "use server" file can only export async functions, found object.

La raison est logique : chaque export devient un point d'entrée HTTP. Un objet ne peut pas en être un. Les types, eux, ne comptent pas : ils sont effacés à la compilation, il n'en reste rien à l'exécution. C'est pourquoi ReservationState et INITIAL_STATE vivent désormais dans components/reservation.ts.

Le point à ne jamais oublier

La référence vers l'action est publique. N'importe qui peut envoyer la même requête POST sans jamais ouvrir votre page, avec les données de son choix. Une Server Action doit donc être traitée exactement comme une route d'API publique : on ne fait confiance à rien de ce qui arrive.

3.3Promise, async, await

Le serveur passe son temps à attendre : une lecture d'en-têtes, un appel réseau, une base de données. JavaScript ne bloque pas pendant ces attentes — il utilise des promesses.

Une Promise<T> est un jeton : « la valeur de type T n'est pas là maintenant, mais elle arrivera ». Le générique dit ce qu'elle finira par contenir.

async devant une fonction a deux effets : il autorise await à l'intérieur, et il enveloppe automatiquement le retour dans une promesse. Même si le corps fait return { status: "sent" }, le type de retour réel est Promise<ReservationState>.

await fait l'inverse : il attend qu'une promesse aboutisse et en extrait la valeur.

L'erreur la plus fréquente

Oublier await. Vous manipulez alors la promesse elle-même au lieu de son contenu, et vous obtenez des messages déroutants du genre « Property 'get' does not exist on type 'Promise<HeadersList>' ».

3.6État en mémoire et fermetures

Le limiteur de débit illustre une notion importante : un module serveur garde son état entre les requêtes, tant que le processus vit.

Ce qu'il faut y voir :

  • seen est déclaré au niveau du module. Il est créé une fois, au premier chargement, et survit à toutes les requêtes suivantes. C'est une variable globale au processus.
  • (at) => now - at < WINDOW_MS est une fermeture (closure) : cette petite fonction, passée à .filter(), se souvient de now et de WINDOW_MS définis à l'extérieur d'elle. C'est un mécanisme fondamental de JavaScript, et vous le croiserez partout.
  • for (const [id, hits] of seen) parcourt la Map. Chaque tour donne un couple [clé, valeur], ici déstructuré immédiatement en deux variables.
  • .every(…) renvoie vrai si tous les éléments satisfont le test. Son pendant, .some(…), renvoie vrai si au moins un le satisfait — c'est celui que validateReservation utilise pour vérifier le slug.
Les limites de cette approche

Parce que seen vit en mémoire, il est remis à zéro à chaque redéploiement, et il n'est pas partagé si le site tourne sur plusieurs instances. C'est assumé et documenté dans le commentaire du fichier : c'est un ralentisseur, pas un mur. Une vraie protection passerait par Redis, où l'état est partagé et persistant.

3.8fetch et le monde extérieur

Les points à relever :

  • fetch est intégré à Node.js moderne. C'est pourquoi ce projet n'a installé aucune dépendance pour envoyer des emails : la bibliothèque officielle de Resend ne ferait qu'envelopper cet appel.
  • { from, to: [to], subject, text, html } — quand la variable porte déjà le nom de la clé, on peut écrire juste from au lieu de from: from. C'est le raccourci de propriété.
  • ...(replyTo ? { reply_to: replyTo } : {}) — les trois points sont l'opérateur de décomposition (spread). Il étale le contenu d'un objet dans un autre. Combiné à un ternaire, il permet d'ajouter une clé conditionnellement : si replyTo est vide, on étale un objet vide, et la clé n'existe tout simplement pas.
  • JSON.stringify transforme l'objet JavaScript en texte JSON, format attendu par l'API.
  • response.ok est vrai pour un statut HTTP de 200 à 299. Point crucial : fetch ne lève pas d'exception sur une réponse 400 ou 500. Il ne rejette que si le réseau lui-même échoue. Sans ce test if (!response.ok), un refus de l'API passerait complètement inaperçu et l'utilisateur verrait « envoyé ».
Le type de retour de deliver

deliver renvoie Promise<boolean> : vrai si c'est parti, faux sinon. Cette valeur remonte jusqu'à return ok ? { status: "sent" } : { status: "failed" }. La chaîne est complète : un refus de l'API de Resend se traduit par un message honnête affiché au visiteur.

Partie 4

React et TSX

Ce qui se passe de l'autre côté de la frontière : comment l'interface est décrite, et comment les hooks sont typés.

4.1Un composant est une fonction

Un composant React est une fonction qui prend un objet de propriétés (les props) et renvoie une description de ce qu'il faut afficher. C'est tout.

Deux conventions non négociables : le nom commence par une majuscule (React distingue les composants des balises HTML par là), et la fonction est pure au sens où on l'appelle sans rien faire d'autre.

Notez le type de onBack : () => void. Cela se lit « une fonction qui ne prend aucun argument et ne renvoie rien ». Passer une fonction en propriété est le mécanisme standard pour qu'un enfant prévienne son parent qu'il s'est passé quelque chose.

4.2La syntaxe TSX

TSX, c'est TypeScript plus la syntaxe de balises. Ces balises ne sont pas du HTML : ce sont des appels de fonction déguisés, transformés à la compilation.

En HTMLEn TSXPourquoi
class="x" className="x" class est un mot réservé de JavaScript

<br> <br /> Toute balise doit être fermée

Les accolades { } font sortir du mode balise pour revenir au mode JavaScript :

  • className={styles.submit} — accolades : la valeur est une variable JavaScript.
  • type="submit" — guillemets : une chaîne littérale.
  • disabled={pending} — un booléen ; le bouton se désactive pendant l'envoi.
  • {pending ? … : …} — entre les balises, les accolades insèrent le résultat d'une expression. Le libellé change pendant l'envoi.

L'attribut étalé

{...objet} étale les clés de l'objet comme autant d'attributs. Ici, les attributs d'accessibilité ne sont ajoutés que si le champ est en erreur — sinon on étale {} et rien n'est ajouté. C'est le même opérateur de décomposition que dans le corps de la requête à Resend (section 3.8).

4.4L'état : useState

Un composant est réexécuté chaque fois que son affichage doit changer. Une variable ordinaire serait donc réinitialisée à chaque fois. useState est la mémoire qui survit à ces réexécutions.

useState renvoie un tableau de deux éléments, qu'on déstructure aussitôt : la valeur, et la fonction qui la change. Appeler setView(...) demande à React de réafficher le composant avec la nouvelle valeur.

Quand faut-il le générique ? Quand la valeur initiale ne suffit pas à deviner le type.

  • useState(false) — inutile de préciser : c'est un boolean.
  • useState<OverlayView>(null) — indispensable. Sans le générique, TypeScript déduirait null tout court, et setView({ type: "detail", slug }) serait refusé.

Deux subtilités. D'abord, seule la valeur est extraite — il n'y a pas de setter, la date d'ouverture ne changera pas. Ensuite, l'argument est une fonction et non une valeur : c'est l' initialisation paresseuse. React ne l'appelle qu'au premier rendu. Écrire useState(isoDate(new Date())) recalculerait la date à chaque réaffichage pour rien.

4.5Les effets : useEffect

useEffect sert à tout ce qui n'est pas « calculer l'affichage » : s'abonner à un événement, lancer une animation, parler à une bibliothèque extérieure. Le code s'exécute après que React a mis à jour le DOM.

Les trois parties d'un effet :

  1. Le corps — ce qui s'exécute. Ici : brancher deux écouteurs d'événements.
  2. Le retour — la fonction de nettoyage. React l'appelle quand le composant disparaît, ou avant de rejouer l'effet. Sans elle, les écouteurs s'accumuleraient à chaque montage : c'est une fuite de mémoire classique.
  3. Le tableau de dépendances — [] ici. Vide, il signifie « exécute une seule fois, au montage ». S'il contenait [slug], l'effet serait rejoué à chaque changement de slug.

Le nettoyage est visible aussi dans les effets GSAP du projet, sous une autre forme :

gsap.context enregistre tout ce qui est créé à l'intérieur ; revert() défait le tout d'un coup. Sans cela, les animations d'un composant démonté continueraient d'exister et de manipuler des éléments disparus.

Une ref sert à deux choses : pointer un élément du DOM, ou retenir une valeur sans provoquer de réaffichage.

Le générique indique quel élément la ref pointera : HTMLDivElement pour un <div>, HTMLElement pour un <section>. C'est ce qui donne accès à .scrollWidth, .clientWidth et compagnie avec l'autocomplétion.

4.7Les autres hooks du projet

useActionState — le pont vers le serveur

Trois valeurs, et c'est tout ce dont le formulaire a besoin :

  • state — ce que l'action a renvoyé, du type ReservationState. C'est l'union discriminée de la section 2.5.
  • formAction — à passer à <form action={formAction}>.
  • pending — true pendant l'aller-retour. Il désactive le bouton et change son libellé.

C'est ce hook qui impose la signature (previousState, formData) à l'action serveur, expliquée en 3.5.

useId — des identifiants uniques

Un <label htmlFor> doit désigner un id unique dans toute la page. Écrire id="name" en dur casserait si le composant apparaissait deux fois. useId génère un préfixe garanti unique, et cohérent entre le rendu serveur et le rendu client — ce que Math.random() ne saurait pas faire.

useSyncExternalStore — s'abonner à l'extérieur

La langue n'est pas rangée dans l'état d'un composant : c'est une variable de module, partagée par toute l'application. useSyncExternalStore est le hook prévu pour brancher React sur une telle source extérieure. Il prend trois fonctions : comment s'abonner, comment lire la valeur côté client, comment la lire côté serveur.

Le troisième argument existe précisément à cause de la section 3.1 : sur le serveur, localStorage n'existe pas, donc la valeur y est toujours "en". React compare les deux instantanés et effectue un réaffichage correctif si le visiteur avait choisi le français — au lieu de planter avec une erreur d'hydratation.

useT() montre au passage qu'un hook peut en appeler un autre : c'est ainsi qu'on fabrique ses propres hooks. Le projet en a trois — useT, useLocale et useDropReveal. La convention veut que leur nom commence par use.

Les trois façons d'afficher conditionnellement

Le troisième mérite une explication : a && b donne b si a est vrai, et a sinon. Comme React n'affiche rien pour false, cela revient à « affiche ceci seulement si la condition tient ».

Le piège du && avec un nombre

{items.length && <Liste />} affiche littéralement 0 quand la liste est vide — car 0 est faussé, mais React affiche le nombre zéro. Préférez {items.length > 0 && …}, qui produit un vrai false.
